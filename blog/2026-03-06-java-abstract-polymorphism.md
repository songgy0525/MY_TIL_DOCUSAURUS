## 1. 학습 체크리스트와 로드맵

체크리스트 목적: "뭘 모르는지 모르는 상태"에서 "N번 항목이 이해가 안 된다"로 질문을 구체화.

| 로드맵 요소 | 강조 이유 |
|------------|----------|
| DB 학습 | 문법이 정형화되어 있어 자바 이후 부담 분산 가능 |
| 디자인 패턴 | "자바를 잘한다"는 인식과 직결 |
| 스트림/람다 | Spring 등에서 화살표 문법이 빈번 — 미숙하면 코드 이해 어려움 |
| I/O | 개념 확장에 도움, 필수는 아님 |

**핵심 키워드:** `체크리스트` `디자인패턴` `스트림` `람다` `원격데스크톱`

## 2. 인터페이스 vs 추상 클래스

| 구분 | 인터페이스 | 추상 클래스 |
|------|-----------|------------|
| 핵심 성격 | 기능 계약 (추상 메소드 집합) | 일반 클래스 + 추상 메소드 가능 |
| 생성자 | 없음 | 있음 |
| 구현 강제 | 미구현 메소드 반드시 오버라이딩 | 동일 |
| 필드 | 자동 `public static final` | 일반 클래스 규칙 적용 |
| 다중 상속 | 가능 | 불가 |

:::info
추상 메소드가 클래스에 포함되면 해당 클래스는 반드시 `abstract`로 선언해야 한다.

추상 클래스는 추상 메소드가 없어도 `new`로 직접 인스턴스화 불가 선언이 가능.
:::

:::info
클래스 다중 상속이 제한되는 이유: 생성자 호출 및 정체성(특성) 충돌.
:::

**핵심 키워드:** `extends` `implements` `abstract` `default메소드` `static`

## 3. 추상 메소드 구현 흐름 실습

`인터페이스 → 추상 클래스(일부 구현) → 자식 클래스(나머지 구현)` 단계적 구현 모델.

```java
interface IParent {
    void make();
    void print();
}

abstract class AParent implements IParent {
    @Override
    public void print() {
        System.out.println("AParent.print()");
    }

    @Override
    public abstract void make(); // 자식에게 위임
}

class Child extends AParent {
    @Override
    public void make() {
        System.out.println("Child.make()");
    }
}
```

:::warning
추상 메소드를 선언하는 순간 클래스에 `abstract`가 없으면 컴파일 오류 발생.

IDE의 "abstract 선언 추가" 제안으로 즉시 확인 가능.
:::

:::info
클래스 다이어그램을 읽는 능력이 VMI(동적 바인딩) 이해에 필수.

상속/구현 관계를 그림으로 읽어야 런타임 호출 대상 추적 가능.
:::

**핵심 키워드:** `추상메소드` `추상클래스` `오버라이드` `클래스다이어그램` `컴파일오류`

## 4. 다형성, VMI와 메모리 노출

| 구분 | 결정 기준 |
|------|----------|
| 접근 가능한 멤버 | 참조 변수의 타입 |
| 오버라이딩된 메소드 실행 | 실제 생성된 객체 타입 (VMI) |
| 필드 접근 | 참조 변수의 타입 (하이딩) |
| static 메소드 | 클래스 기준 (하이딩) |

```java
// IParent 타입으로 참조해도 make() 호출은 최종 구현(Child)으로 이동
IParent p = new Child();
p.make(); // Child.make() 실행
```

- 자식 타입으로 생성 → 자식 멤버까지 모두 접근 가능
- 부모 타입으로 업캐스팅 → 부모 타입에 선언된 멤버만 접근 가능
- 업캐스팅 상태에서도 오버라이딩된 메소드는 실제 객체의 구현이 실행됨

**핵심 키워드:** `다형성` `업캐스팅` `다운캐스팅` `VMI` `동적바인딩`

## 5. H2O 모델링 예고

다음 실습 구조 예고:

| 구성 요소 | 역할 | 예시 명명 |
|----------|------|----------|
| 인터페이스 | 기능(행동)의 계약 정의 | `H2O` |
| 추상 클래스 | 공통 로직/기본 틀 제공 | `H2OImpl` |
| 구체 클래스 | 상태별 동작 완성 | `Ice`, `Water`, `Steam` |

:::info
실무 관례: 인터페이스 구현체에 `Impl` 접미사를 붙이는 네이밍 패턴.

프레임워크/엔터프라이즈 코드에서 구현 클래스를 빠르게 식별하기 위한 관습.
:::

**핵심 키워드:** `H2O` `Impl` `추상화` `구현체` `상태모델링`

## 오늘의 핵심 요약

1. 인터페이스 = 기능 계약 (생성자 없음, 필드는 자동 `static final`)
2. 추상 클래스 = 일반 클래스 + 추상 메소드 가능 (생성자 있음)
3. 추상 메소드 있으면 클래스도 반드시 `abstract`
4. VMI = 참조 타입으로 노출 범위 제한 + 실제 객체 타입으로 메소드 실행
5. 업캐스팅 시 멤버 노출은 참조 타입 기준, 메소드 실행은 실제 객체 기준
6. 구현체 클래스명에 `Impl` 접미사 붙이는 것이 실무 관례
